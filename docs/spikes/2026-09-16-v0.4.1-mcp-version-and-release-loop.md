# 2026-09-16 · v0.4.1：一个自相矛盾的产物，和它是怎么被拦下的

日期：2026-09-16 01:41 – 02:05 CST。接 `2026-09-16-english-launch-deployed-and-v0.4.0.md`。

## 发生了什么

打完 `v0.4.0` 之后，`main` 上的 CI 红了一次：`cli/tests/mcp.rs` 的握手断言比对 `serverInfo.version` 与 `env!("CARGO_PKG_VERSION")`，实际收到 `0.3.0`、期望 `0.4.0`。

原因是 `cli/src/mcp.rs` 里 `#[tool_handler(version = "…")]` 只接受字面量，版本号是从 `Cargo.toml` 手抄过去的一份，我只改了 `Cargo.toml`。那段代码上方的注释早就写着「抄岔了，tests/mcp.rs 里那条握手测试会挂」——这条测试就是为这件事设的，它按设计生效了。

试过让它自动跟随：`version = env!("CARGO_PKG_VERSION")` 编不过，宏报 `Unexpected type 'macro'`，确认注释里的说法属实，只能保持手抄 + 测试兜底。

## 为什么补一个 0.4.1 而不是留到下次

`v0.4.0` 的包已经传到 Releases 与 R2，而那个二进制 `--version` 说 `0.4.0`、MCP 握手说 `0.3.0`。功能上无害，但它是一个会对外说假话的产物。发布链路这时已经全自动（R2 上传步骤在 v0.4.0 那次第一次真正跑通），补一版的成本只有一次 CI，所以补。

同时把四处版本号一次对齐：`cli/Cargo.toml`、`cli/src/mcp.rs` 的字面量、`deploy/site/install.sh` 的兜底版本、`deploy/site/index.html` 里「The current release is …」那句。

## 验证（真机）

`v0.4.1` 五个 target 全绿，R2 的 `VERSION` 变为 `v0.4.1`。空 `HOME` 重新走一遍：

```
$ curl -fsSL https://playtest.run/install.sh | bash
$ playtest --version
playtest 0.4.1
$ echo '{"jsonrpc":"2.0","id":1,"method":"initialize",…}' | playtest mcp
serverInfo: {"name": "playtest", "version": "0.4.1"}
```

两处一致。
