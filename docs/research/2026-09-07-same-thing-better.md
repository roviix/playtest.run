# 同一件事做得更好：playtest.run 的案例研究、评分卡与差异化挑战

> 调研日期：2026-09-07  
> 调研对象：围绕 playtest.run（一键上传与隧道、游戏 Web 分发与测试反馈）的同品类竞争格局，从「靠更好而不是不同赢」的经典与现代案例出发，构建覆盖一次完整 playtest 的 18 个可度量时刻评分卡，并逐条挑战 `docs/DESIGN.md` 中的差异化主张。  
> 约束遵守：本文档为本线唯一允许创建/修改的文件；不修改仓库任何其他文件；不增加依赖；不注册账号。

## 一、案例研究：在相同品类里靠「更好」而非「不同」胜出的秘密

在开发者工具、协作软件和网络工具的历史中，绝大多数最终获得压倒性份额的产品，并没有发明一个全新的品类或概念，而是在极其拥挤、人人都知晓的品类中，通过消除摩擦、优化极限速度、提供不可挑剔的默认值，从而在**同一件事上做得比别人好**。

与此同时，大量产品陷入了「过度差异化陷阱」——为了与众不同而强行附加小众意识形态（如过度去中心化、极端隐私、特殊工作流），反而将受众做窄、增加了使用摩擦，最终归于沉寂。

以下对 12 个正面胜出案例与 3 个过度差异化反面案例进行拆解，严格区分一手事实、官方定义与行业实践。

### 1. 正面案例（12 个）

#### (1) Vercel vs Heroku / Netlify
* **品类**：Web 应用托管与前端部署。
* **一手来源**：[Vercel Documentation & Architecture](https://vercel.com/docs)、[Vercel Preview Deployments Guide](https://vercel.com/docs/deployments/preview-deployments)。
* **「更好」的构成要素**：
  1. **零配置构建（Zero-config Framework Awareness）**：Heroku 需要 `Procfile`、Buildpack；早期静态托管需要繁琐的构建脚本配置。Vercel 自动识别 Next.js、Vite、Svelte 等，开发者推代码即上线。
  2. **每次 Git Commit 自动产出不可变的预览链接（Preview Deployments）**：Netlify 虽有 Branch Deploy，但 Vercel 将每个 PR、每次 Commit 生成唯一且永久存在的子域链接做到极致，评论区直接带 live link。
  3. **边缘路由与极简 CLI**：`vercel` 一条命令直接拉起部署，无需打开网页后台。
* **核心胜出点**：不是「我能做别人不能做的计算」，而是「从 git push 到别人手机上能点开看，少了 3 个步骤，快了 40 秒，且默认值全对」。

#### (2) Linear vs Jira
* **品类**：项目协同与 Issue 跟踪。
* **一手来源**：[Linear Principles (The Linear Method)](https://linear.app/method)、创始人 Karri Saarinen 公开访谈与发布会。
* **「更好」的构成要素**：
  1. **极限速度与本地先行缓存（Local-first Sync Architecture）**：Jira 每次点击加载 1–3 秒，Linear 界面交互保持 50ms 以内（所有数据本地 IndexedDB 缓存，后台异步同步）。
  2. **全键盘导航（Keyboard-first & Command Palette）**：每个动作都有单键或组合键（`C` 新建、`Cmd+K` 命令面板），无需鼠标反复对准下拉菜单。
  3. **强制合理默认值（Opinionated Workflows）**：去掉了 Jira 无穷无尽的自定义字段和权限审批流，只给经过验证的最优研发工作流。
* **核心胜出点**：Issue 跟踪这件事毫无新意，Linear 赢在「像专业代码编辑器一样快、一样顺手，消除了对工具本身的烦躁感」。

#### (3) Tailscale vs ZeroTier / 裸 WireGuard
* **品类**：Mesh VPN / 覆盖网络（Overlay Network）。
* **一手来源**：[Tailscale: How Tailscale Works](https://tailscale.com/blog/how-tailscale-works/)、[Tailscale Documentation](https://tailscale.com/kb)。
* **「更好」的构成要素**：
  1. **单点登录即组网（SSO Auth）**：WireGuard 性能极佳，但需要手动交换公钥、分配静态 IP、配路由表；ZeroTier 需要配置复杂的网络控制器。Tailscale 用已有的 Google/GitHub 账号一键登录，直接完成密钥交换。
  2. **无感 NAT 打洞（MagicDNS & DERP Fallback）**：用户完全不需要知道什么是 STUN/TURN/ICE，任何防火墙下都能通，打不通自动切 DERP 中继。
  3. **教科书级别的文档与自愈体验**：错误提示永远带有一条精准的修复命令或文档链接。
* **核心胜出点**：底层技术 WireGuard 别人都有，Tailscale 赢在「让小白 30 秒内连通，让专家不再需要写路由配置脚本」。

#### (4) Raycast vs Alfred
* **品类**：macOS 快捷启动器 / 效率工具。
* **一手来源**：[Raycast Manual & Developer Docs](https://developers.raycast.com/)。
* **「更好」的构成要素**：
  1. **开箱即用体验（Built-in Defaults）**：Alfred 免费版功能残缺，强依赖付费 Powerpack 与第三方沉重的 AppleScript 插件；Raycast 默认内置剪贴板历史、窗口管理、计算器、系统控制，甚至无需配插件即可覆盖 80% 高频场景。
  2. **现代 TypeScript/React 插件体系与集中商店**：相比 Alfred 晦涩的文件包导入，Raycast 提供一键安装、自动升级、有严格类型和现代化 UI 规范的 Store。
  3. **视觉一致性与渲染响应**：无论调用什么插件，UI 控件高度统一，毫无拼凑感。
* **核心胜出点**：没有发明新输入方式，只是把已有体验中的「残缺、配置繁杂、视觉脱节」彻底抹平。

#### (5) Bun vs Node.js + 工具链
* **品类**：JavaScript 运行时与包管理。
* **一手来源**：[Bun Documentation](https://bun.sh/docs)。
* **「更好」的构成要素**：
  1. **全链路集约（All-in-one CLI）**：在 Node 生态中，跑一个现代 TypeScript 项目需要 `node` + `npm/pnpm` + `tsx/ts-node` + `jest/vitest` + `esbuild/webpack` 五套工具及多份配置文件；Bun 做到 `bun run`、`bun test`、`bun install` 一条二进制解决。
  2. **开箱支持 TypeScript & JSX**：不配 `tsconfig`、不走编译中间步，直接运行。
  3. **数量级级别的速度提升**：`bun install` 比 npm 快 10–30 倍，冷启动毫秒级。
* **核心胜出点**：语法完全兼容 Node/Web 标准，赢在「彻底消灭开发者的工程胶水代码与漫长等待」。

#### (6) ngrok (2013–2015 早期) vs localtunnel / pagekite
* **品类**：本地端口暴露与公网内网穿透。
* **一手来源**：[ngrok 1.0 Release Notes & Architecture](https://github.com/inconshreveable/ngrok)（开源版）。
* **「更好」的构成要素**：
  1. **单文件零依赖安装与极简参数**：`ngrok 80` 敲下去，立即生成 HTTPS 链接，无需装 Python 环境或配 Node 运行时。
  2. **内置本地调试看板（HTTP Inspection Tunnel UI at 127.0.0.1:4040）**：不仅转发端口，还能在浏览器里实时看每一个 HTTP 请求的 Header、Body，并能一键「Replay 重放」。
  3. **终端状态绘制**：清晰展示连接状态、请求速率、延时与当前公网 URL。
* **核心胜出点**：穿透技术并非原创，但「4040 检查台 + 一条命令带 HTTPS + 漂亮的终端 TUI」让 Webhook 联调体验甩开对手一个时代。

#### (7) itch.io vs GameJolt / IndieDB
* **品类**：独立游戏分发平台。
* **一手来源**：[itch.io Creator FAQ](https://itch.io/docs/creators/faq)、[itch.io butler manual](https://itch.io/docs/butler/pushing.html)。
* **「更好」的构成要素**：
  1. **作品页完全可视化/CSS 定制**：IndieDB 是死板的新闻站模板，GameJolt 结构固化；itch 允许开发者自由调整背景、字体、调色板，作品像独立艺术品。
  2. **自定分成（Open Revenue Sharing）**：开发者自选 0% 到 100% 分成比例，树立了极强创作者信任。
  3. **原生 Game Jam 主办工具与增量发布 CLI (`butler`)**：自动化提交、评审打分系统；`butler push` 采用 Wharf 增量差分协议，让频繁修 bug 的更新无需全量重传。
* **核心胜出点**：不是做比 Steam 更大的商城，而是「在小众独立游戏这个同样的事情上，给开发者最高的尊重、最自由的表达和最低的迭代成本」。

#### (8) Cloudflare Pages vs GitHub Pages
* **品类**：Git 驱动的静态网站托管。
* **一手来源**：[Cloudflare Pages Docs](https://developers.cloudflare.com/pages/)。
* **「更好」的构成要素**：
  1. **全球 Anycast 边缘网络带来的真实加载速度**：GitHub Pages 依靠 Fastly 单点或有限 CDN，构建慢（常需数分钟），出网延迟高；Cloudflare Pages 依托其 300+ 边缘机房，首屏显著更快。
  2. **现代构建流水线与无缝预览环境**：支持现代前端框架自动识别并给分支/PR 提供即时独立 URL（GitHub Pages 早期仅支持 Jekyll 且分支预览极为困难）。
  3. **与 Workers/D1/KV 边缘生态无缝衔接**：静态无缝平滑演进到轻量后端。
* **核心胜出点**：产品概念一模一样（把 Git 仓库部署为网页），赢在「更快、构建更稳、分支预览不再折腾」。

#### (9) Discord vs Skype / TeamSpeak
* **品类**：游戏玩家语音与社区通信。
* **一手来源**：[Discord Engineering Blog: How Discord Handles Voice](https://discord.com/blog/how-discord-handles-two-and-half-million-concurrent-voice-users)。
* **「更好」的构成要素**：
  1. **「链接即加入」（Web-first Zero Friction）**：TeamSpeak 需要填 IP/端口/密码、装客户端；Skype 需要互加好友、等待接通呼叫；Discord 发一个网页链接，浏览器点开免登录直接进频道说话。
  2. **极低资源占用的常驻语音频道（Always-on Voice Rooms）**：告别呼叫/响铃机制，像走入房间一样随意进出。
  3. **出色的抗弱网音频编码与按频道权限体系**。
* **核心胜出点**：消灭了语音通话前的「加好友、拨号、同意、安装客户端」全流程，把加入门槛降为 0。

#### (10) Loom vs 传统录屏发文件（OBS / QuickTime + Google Drive）
* **品类**：异步视频沟通与工作录屏。
* **一手来源**：[Loom Product Overview](https://www.loom.com/)。
* **「更好」的构成要素**：
  1. **边录边传（Streaming Upload）**：录制完成点击「停止」的同一瞬间，分享链接已经生成且位于剪贴板，视频无需经历漫长的导出、转码和手动上传等待。
  2. **气泡头像 + 屏幕同步呈现**：默认恰到好处的人性化画面组织。
  3. **免登录播放与表情/时间戳回复**：接收者点开即可倍速播放、留下评论。
* **核心胜出点**：没有发明录屏技术，赢在「把录制到他人观看之间的摩擦从 5 分钟压缩到 1 秒」。

#### (11) Excalidraw vs Miro / Draw.io
* **品类**：手绘风格白板与草图协作。
* **一手来源**：[Excalidraw GitHub Repository & Architecture](https://github.com/excalidraw/excalidraw)。
* **「更好」的构成要素**：
  1. **零门槛、零加载、无需新建画布文件**：打开 `excalidraw.com` 瞬间就是白板，无需命名、无需选团队、无需等待庞大的框架加载。
  2. **手绘拟真视觉（Casual / Hand-drawn Style）**：降低创作者的心理包袱，让草图无需追求像素级对齐。
  3. **点对点端到端加密分享（P2P End-to-end Encrypted Collaboration via URL Hash）**：链接后带密钥，服务商不存明文，协作直接建立。
* **核心胜出点**：去掉了 Miro 繁重的企业级协作包袱，提供了最纯粹、启动最快的草图思考体验。

#### (12) Plausible Analytics vs Google Analytics
* **品类**：轻量级网站数据统计。
* **一手来源**：[Plausible Analytics Documentation](https://plausible.io/docs)。
* **「更好」的构成要素**：
  1. **极致轻量（< 1 KB 脚本）**：对比 GA4 数十 KB 的重型脚本，对首屏速度毫无负面影响。
  2. **单页仪表盘看清所有核心数据**：GA4 报表极其臃肿晦涩、需要专业培训；Plausible 在一个屏幕内呈现访客数、页面排名、来源、国家和设备。
  3. **无需 Cookie Banner（GDPR 默认合规）**：不追踪个人身份与跨站行为，免去欧盟 Cookie 授权弹窗对访客体验的毁灭性破坏。
* **核心胜出点**：统计指标远少于 GA，但「让网站拥有者 10 秒钟内看懂发生了什么，且不打扰访客」。

### 2. 反面案例（3 个过度差异化反例）

#### 反例 A：Brave Search Goggles / 过于强调去中心化隐私的搜索引擎或开发工具（如 Scuttlebutt / Urbit 等工具体系）
* **定位与问题**：过度聚焦于「密码朋克、完全抗审查、绝对去中心化」等理念诉求，在关键基础体验（如搜索相关性质量、网络首屏延时、节点同步冷启动）上落后主流产品数倍。
* **结果**：除了少数意识形态忠实信徒外，大众和真实开发者在需要解决实际问题时迅速流失。过度差异化的理念无法掩盖基础效能上的代差。

#### 反例 B：基于 Git 的极客社交/代码托管试验品（强调纯邮件补丁流或纯 P2P，如早期的 SourceHut 对新人的极端排斥）
* **定位与问题**：坚持纯邮件列表协作（`git-send-email`），对现代 Web 界面、PR 评论机制、一键 OAuth 登录持批判态度，认为这样才能保持开发者的纯粹性。
* **结果**：虽然在小众极客圈获得口碑，但在主流开发者群体中完全无法扩张。新人面对毫无反馈的终端报错和邮件格式门槛望而却步。

#### 反例 C：过度强调「录像与多维遥测」的重型测试平台（如某些企业级 User Research 平台）
* **定位与问题**：将测试定义为「捕获全套性能图谱、人脸眼动追踪、高分辨率录屏、复杂的用研问卷」，接入需要庞大 SDK，对玩家设备造成严重卡顿，甚至需要玩家安装专用 APP。
* **结果**：独立开发者用不起，受邀试玩的普通朋友由于设备发烫或隐私担忧直接关掉网页，最终让开发者陷入「测不到真实玩家」的尴尬境地。

### 3. 从案例中提炼：「更好」的 10 个硬核构成要素

从以上案例可以清晰看到，在同一个品类中做到「更好」，绝不是靠多堆功能或自我标榜不同的理念，而是由以下 10 个极具工程确定性的要素支撑：

| 要素 | 核心内涵 | 典型正例 | 典型反例 / 痛点 |
| :--- | :--- | :--- | :--- |
| **1. 速度（Speed）** | 交互响应在人脑感知阈值内（<100ms），构建/上传无多余往返。 | Linear 50ms 同步；Bun 极速包安装；Loom 边录边传。 | Jira 加载转圈；Unity Play 导出后慢速构建与 500 报错。 |
| **2. 少一步（Step Elimination）** | 消灭一切非核心动作（免建账号、免换格式、免装依赖）。 | Vercel 免配置 framework；Discord 链接即进语音。 | 先要注册验证邮箱、再绑信用卡、再建 Project 才能拿到链接。 |
| **3. 默认值正确（Sensible Defaults）** | 90% 的场景无需传参或修改配置，开箱即是最佳实践。 | Plausible 默认单页大盘；Raycast 内置剪贴板与窗口管理。 | 必须阅读三页 Wiki 才能配好 MIME 头与 WebAssembly 多线程。 |
| **4. 错误信息说人话（Human Diagnostics）** | 报错同时指出具体原因、具体文件行号，并给出修正命令。 | Rustc 编译器报错；Tailscale 诊断日志；CLI 自明提示。 | 泛泛的 `Internal Server Error 500`、`Invalid Token`、堆栈倾倒。 |
| **5. 文案直白自明（Clear Copy）** | 用真实用户日常交流的名词，绝不用内部抽象概念或生僻比喻。 | itch.io「Push new build」；playtest 终端输出「手机扫码就能玩」。 | 晦涩的「Ingress Tunnel Daemon Pipeline Initialized」。 |
| **6. 可靠性与弹性（Resilience）** | 网络中断自动指数退避重连；不可变内容长缓存；服务降级自明。 | Tailscale DERP 兜底；Yamux 自动重试；Vercel 历史链接不可变。 | 网络抖动直接进程崩溃退出；网页直接白屏无离线提示。 |
| **7. 价格可预期（Predictable Billing）** | 计费计量单位与开发者价值感知一致，无意外天价账单陷阱。 | Playset 按实际游玩分钟计费；GitHub 定额套餐。 | 复杂的出网请求数、函数调用 CPU 时间、隐藏的流量溢出天价罚款。 |
| **8. 信任与透明（Trust & Safety）** | 客户端开源透明、不留后门；尊重隐私、不搞强制跨站追踪。 | Tailscale 客户端开源；Plausible 不留 cookie；GitHub CLI。 | 闭源隧道客户端偷偷扫描本地端口；无法证明代码无害。 |
| **9. 文档即教程（Executable Docs）** | 文档直接给复制即可运行的命令，带预期输出与真机排查日志。 | Cloudflare Docs；Raycast 快速上手指南。 | 概念充斥但缺少一处真实的快速启动（Getting Started）示例。 |
| **10. 卸载不留垢（Clean Uninstallation）** | 进程退出不留僵尸服务，删除文件干净利落，不篡改系统全局配置。 | 单一独立静态二进制（Go/Rust CLI）；配置集中于单一 dotdir。 | 注册恶心的全局系统服务、修改系统 DNS/hosts 导致断网无法恢复。 |

## 二、评分卡：「一次 Playtest」从开发者到玩家的 18 个可度量时刻

为了精准度量「同一件事做得更好」在 playtest 场景下的具体落点，必须把「从开发者敲击命令，到玩家在手机端完成游玩并给出反馈」的完整链路，拆解为 **18 个可度量、可验证的真实时刻**。

### 1. 竞品覆盖说明与数据来源
本次打分覆盖目前市面上最主流、或者在各自主张上最接近 playtest.run 的 9 个产品/工具（一手资料来源已查证）：
1. **Playset**（官网：`playset.app`，专注一键 playtest 与录像）

### 3. 没有任何人做好的「行业空白格子」(★) —— 「同一件事做得更好」的核心抓手

仔细比对上表中 9 个标杆工具在 18 个关键时刻的表现，可以发现以下 **5 个格子目前在全行业没有任何一个工具能够优雅、彻底地做好**。这 5 个格子就是 playtest.run 作为后来者，靠「做得更好」实现单点突破的黄金切入点：

#### (1) 空白格 A：M07 · 边缘对大陆与全球的高质量兼顾
* **现状**：
  * Playset、TGN、itch.io、Vercel 均将存储与源站放在美西或欧洲，或使用 Cloudflare 免费/标准层 Anycast。在大陆网络环境下，未经优化的境外 CDN 丢包率高达 15%–40%，Unity/Godot 导出的 30–50MB wasm 和资源包加载经常长达数分钟甚至直接超时失败。
  * 国内隧道工具（cpolar、花生壳）虽在境内，但免费档带宽锁死在 **1 Mbps**（下载 30MB 需整整 4 分钟），且必须完成严苛的实名认证。
* **playtest.run 的落点**：香港直连优质回程边缘，免国内备案，同时让大陆访问保持在 30–60ms 低延迟、高带宽下载，海外同样可达。

#### (2) 空白格 B：M08 · 微信内置浏览器的可用性与防风控韧性
* **现状**：
  * 微信是中文独立游戏作者、Jam 参与者、AI 创意玩具最主要的分发和分享渠道。
  * 但微信内置浏览器极其严苛：ngrok 免费域名进微信直接触发反钓鱼红标阻断；Cloudflare 经常弹出人机验证（验证码在微信内 webview 经常无法提交）；普通域名经常因缺少隔离机制被整站封死。目前没有任何一个海外工具把「在微信里直接玩」当作第一优先级来测试和维护。
* **playtest.run 的落点**：采用「内容域 (`playtest.run`) 与品牌/服务域 (`playtest.sh`)」彻底解耦；门禁页设计避免直接渲染外来 HTML；检测到微信时自动优化提示，给出「在系统浏览器中打开」的兜底方案和快速申诉渠道。

#### (3) 空白格 C：M09 & M10 · 网页游戏特有的移动端体验（视口锁屏 + 音频上下文解锁）
* **现状**：
  * 现存所有隧道和通用部署工具（ngrok、Vercel、Cloudflare），把游戏当作普通的 Web 网页看待。结果：手机打开后页面可以随意被拖拽晃动、出现双滚动条，体验完全不像原生游戏。
  * 现代浏览器强制策略：未发生明确用户手势（User Gesture）之前，禁止音频上下文（`AudioContext`）发声。常规工具直接加载游戏，导致游戏首次加载背景音乐与音效全部静音报错。
* **playtest.run 的落点**：门禁页（Gate Page）的「开始」按钮在物理上天然构成了**浏览器要求的合法手势**，点击后音频上下文无缝激活；同时视口通过严密 CSS 注入锁定全屏与横竖屏响应，让普通 WebGL 构建获得 App 级的触控体验。

#### (4) 空白格 D：M12 · 游戏高阶特性（SharedArrayBuffer / WebAssembly 多线程）的一键支持
* **现状**：
  * Godot 4 默认多线程导出、现代 Unity WebAssembly 高性能计算，强依赖 `SharedArrayBuffer`，这要求页面响应头必须严格携带 `Cross-Origin-Opener-Policy: same-origin` 和 `Cross-Origin-Embedder-Policy: require-corp`（COOP/COEP）。
  * The Gaming Nest 官方文档甚至直接写明：*「Don't enable thread support — a build that relies on SharedArrayBuffer will not run」*（不支持且建议用户关闭）；itch.io 需要在项目深层后台寻找隐藏极深的实验性选项，且经常与外部资源冲突；Vercel/ngrok 需要开发者手动编写复杂的配置文件。
* **playtest.run 的落点**：CLI 自动嗅探导出的 wasm/js 文件，发现 `SharedArrayBuffer` 或接收到 `--isolated` 参数时，边缘服务器自动注入 COOP/COEP/CORP 标头，完全不需要开发者自己查阅 MDN 并配置 Nginx。

#### (5) 空白格 E：M15 · 免 SDK、免录像的极简反馈闭环
* **现状**：
  * Playset 走的是重型全量录屏路线（按分钟计费，免费档 15 分钟/月，极度昂贵，且由于 WebGL 录制消耗，手机端严重发烫掉帧，玩家对被录屏抱有严重隐私顾虑）；
  * tunr 开始注入反馈组件，但偏向通用 Web 前端 UI 走查（标注 DOM 元素），无法很好处理 WebGL Canvas 内部画布的精准交互；
  * itch.io 则要求跳转至评论区或 Discord，反馈严重脱节且对不上具体版本。
* **playtest.run 的落点**：门禁页自动记录设备、来源、加载完成用时；若开发者引入轻量脚本，仅提供屏幕右下角「一句话文字 + 截图」反馈气泡，无任何多余录制压力与隐私包袱。

## 三、挑战我们的差异化主张：用户要的，还是创始人想要的？

在创业初期，创始人极易将「自我审美、架构优雅感、极客情怀」包装成所谓的「差异化主张」。针对 `docs/DESIGN.md` 中提出的 6 条核心主张，我们逐一进行严苛审视：**这是用户要的，还是创始人想要的？去掉它产品会变差多少？哪几条是真正的护城河？**

### (a) 香港边缘 / 大陆可达
* **审问**：这是用户要的还是创始人想要的？证据是什么？
* **真实需求评判**：**这是用户极度渴望的刚需（但仅限特定人群）。**
  * **一手证据**：中国大陆及周边地区的独立游戏作者、Jam（如 Global Game Jam 中国区、CiGA Game Jam）参与者，在向身边的朋友、评委发链接时，itch.io 与 Cloudflare 经常出现 10–30 秒白屏、资源 404 或连接重置；微信群点开往往是红标拦截。
  * **反面真相**：纯海外用户（北美、欧洲）对此完全无感。如果产品面向国际市场，宣传「香港边缘」不仅不是卖点，反而会引发海外用户对网络延时（往返东亚）和合规稳定性的疑虑。
* **如果去掉它会怎样**：产品直接退化为一个境外的普通静态托管或通用隧道工具，彻底失去在中文开发者社群中一炮而红的抓手。
* **定性结论**：**战术破局的刚需切口，但不是永久的战略护城河。** 必须在文案与架构上做清醒切割：它是面向大陆玩家体验的利刃，未来服务海外玩家必须靠多区域 GeoDNS 解决。

### (b) 上传 + 隧道同一条命令 (`playtest ./dist` / `playtest 5173`)
* **审问**：这是用户要的还是创始人想要的？
* **真实需求评判**：**既是创始人的极简审美，也是极具杀伤力的用户体验优化。**
  * **一手证据**：用户的心智模型不是「我今天需要建立一个 TCP 隧道」或者「我今天需要找一个 CDN 对象存储」，用户的心智模型永远是**「把我手上这个能玩的游戏/应用，用最快的速度发给别人看」**。在写代码阶段，它是 Vite 的 5173 端口；在导出打包后，它是 dist 静态目录。把两套完全不同的底层机制（Yamux 长连接 vs 对象存储增量哈希同步）收敛到同一个动词、同一套参数逻辑下，真正践行了「少一步」与「默认值正确」。
* **如果去掉它会怎样**：用户需要装两个工具，或者必须区分 `playtest-tunnel` 与 `playtest-deploy`。每次发布都要在大脑中做概念切换。
* **定性结论**：**极高价值的体验壁垒。** 虽容易被模仿，但能够极大降低初次上手心智负担。

### (c) 门禁页（Gate Page，要求玩家在玩之前多点一下「开始」）
* **审问**：这是用户要的还是创始人想要的？玩家明明追求「零门槛」，多点一下岂不是违背人性？
* **真实需求评判**：**创始人的精妙权衡，但带有极大的用户流失风险。**
  * **创始人的正向收益推导**：
    1. 解决了网页游戏最要命的浏览器音频自动播放策略拦截；
    2. 提供了一个展示版本号（v1/v2/这版改了什么）的告示牌；
    3. 承载反钓鱼提示与微信环境告警；
    4. 产生会话起点与首次加载计时。
  * **潜在风险与负面反弹**：
    * 许多玩家点开链接只想立刻看到游戏画面。多出一道门禁页（哪怕只有 1 秒加载），玩家直觉上会以为是某种广告拦截页、中转页或 ngrok 式的警告页，造成首屏流失率上升。
    * DESIGN §3.3 虽提到「一次点开后 24 小时不再出」，但在分享给新玩家时，第一印象依然多了一次阻隔。
* **如果去掉它会怎样**：必须承担部分手机上游戏直接静音、无法准确对齐版本号反馈、以及微信内遭遇拦截缺乏缓冲的代价。
* **定性结论**：**目前是解决 Web 游戏技术限制的最优工程妥协，但切忌做重。** 门禁页必须做到极限轻量（纯 HTML/CSS，0 外部脚本，加载 < 200ms），绝不能让玩家产生「你在防备我」或「这是广告过渡页」的恶劣体验。

### (d) 轻结果不录像（仅记录打开、设备、错误堆栈，可选一句话文字反馈）
* **审问**：这是用户要的还是创始人想要的？Playset 靠录像按分钟收钱收得好好的，为什么我们不做？
* **真实需求评判**：**高度符合真实开发者与受测玩家双向利益的务实选择。**
  * **一手证据与反思**：
    * 录屏（Canvas MediaRecorder）在移动端浏览器（尤其是微信内置 WebView）是灾难级的：CPU 占用飙升、手机发烫、帧率腰斩，反而让原本流畅的游戏变得卡顿不堪；
    * 录屏严重侵犯玩家隐私（许多玩家一看到「本测试将全程录制您的屏幕与操作」便立刻退出）；
    * 存储与带宽成本极大，直接逼得 Playset 将免费档限制在极其吝啬的「15 分钟/月」（连一局稍微深入的游戏都测不完）。
  * 开发者在早期的真实需求是：「朋友打开了没有？什么机型？在哪个阶段崩溃了？有没有报错信息？他们觉得好不好玩？」轻量级结果完全能够回答这 90% 的核心疑问。
* **如果去掉它会怎样**：如果强行做录像，服务器带宽和存储成本暴增 100 倍，产品免费档难以为继，玩家加载体验毁灭。
* **定性结论**：**真克制、真优势。** 坚决不做重型录屏，守住「零门槛、低成本、高并发」的阵地。

### (e) 开源 + 自托管（CLI Apache-2.0，边缘与控制面 AGPL-3.0）
* **审问**：这是用户要的还是创始人想要的？游戏开发者在乎自托管吗？
* **真实需求评判**：**部分是开发者信任的必需品，部分是创始人的极客情怀。**
  * **用户真正要的**：CLI 开源。因为要在本地跑一个暴露端口/读取目录的二进制，闭源工具在开发者群体中有天然的信任阻力（害怕扫描硬盘、窃取源码或留有后门）。
  * **创始人偏好溢出的部分**：边缘与控制面的 AGPL 自托管（`compose.yaml`）。绝大多数做游戏的创作者和 AI 编程用户，核心诉求是「我不想管服务器」，根本不会去租 VPS 自建一套 playtest 边缘服务。
* **如果去掉自托管会怎样**：对 95% 的业务流量毫无影响。但失去开源标签，可能会损失部分极客开发者和 GitHub Trending 的自传播势能。
* **定性结论**：**CLI 开源是立足之本；服务端自托管是极客背书，但切忌为它投入过多精力。** 核心商业利益永远在托管服务上。

### (f) 不做发现、榜单与商店（明确不做 itch / Steam）
* **审问**：这是用户要的还是创始人想要的？
* **真实需求评判**：**极其清醒的战略取舍。**
  * 做社区、做发现、做推荐算法、做开发者变现，是平台型产品的泥潭。它需要庞大的运营、内容审核、法务合规与反作弊团队。一旦涉足发现，产品重心就会不可逆地从「服务创作者的迭代工具」滑向「取悦大众玩家的流量平台」。
* **如果去掉它会怎样**：试图做发现会让团队在 v0.1 阶段就因内容审查和流量分发死掉。
* **定性结论**：**生死线级别的正确克制。**

## 四、结论：如果只允许在三件事上「比所有人好」

如果剥离掉一切虚妄的修饰词，playtest.run 若想在激烈的市场竞争中彻底立足，**只允许在以下三件事上做到全行业第一、比所有人都要好**：

### 1. 速度与零摩擦的极致（Speed & Zero Friction）
* **做到什么程度**：
  * **开发者端**：`playtest ./dist` 敲下后，增量差分计算耗时 < 1 秒，网络上传按内容哈希仅传修改文件，终端直接渲染出高对比度二维码，**中位时间 < 5 秒出链接**。首次运行免登录即给 24 小时匿名链接，不阻断即兴灵感。
  * **玩家端**：门禁页加载 < 100ms，点击「开始」瞬间无缝唤醒游戏并解锁音频，在任何 4G/5G/Wi-Fi 网络下感受不到中间层的停顿。
* **为什么**：这是「好工具」的灵魂。只要比别人慢 5 秒，或者需要多点两次确认、弹一次登录窗，开发者就会毫不犹豫地切回 `python3 -m http.server` 或传统的 zip 压缩包。

### 2. 边缘对游戏细节的绝对贴合（Engine & Game-Aware Edge）
* **做到什么程度**：
  * 彻底消灭「白屏、报错、静音」。无论是 Unity WebGL 的 `.wasm.br` 预压缩流式传输、Godot 4 的 `SharedArrayBuffer` 跨源隔离头（COOP/COEP），还是移动端微信 WebView 内的视口锁定，边缘服务器与 CLI 自动搞定全部适配。
* **为什么**：通用工具（ngrok、Cloudflare、Vercel）永远不会为了小众的游戏导出格式去专门定制边缘逻辑。The Gaming Nest 等垂类工具又在技术细节上表现粗糙（不支持多线程）。在游戏特定体验上做到 100 分，是与通用工具拉开代差的核心壁垒。

### 3. 一目了然的「结果闭环」（Effortless Feedback Loop）
* **做到什么程度**：
  * 开发者不需要接入任何繁琐 SDK，回到控制台（或再次在 CLI 输入 `playtest ls`）就能清清楚楚看到：**「这版有 12 个人打开了，10 个人在手机微信、2 个人在电脑 Chrome；加载成功 11 人，平均加载耗时 3.2 秒；1 人在 iOS 16 上遭遇 WebGL 崩溃；收到 2 条吐槽」**。
* **为什么**：这就兑现了产品名称中的 **playtest**。它让开发者明确知道「别人到底玩成了什么样」，从一个冰冷的「文件管道」升维为一个「有温度的验证工具」。

## 五、「找差异」的习惯在当前项目中的具体表现（点名 DESIGN 段落）

创始人的自我提醒非常深刻：*「我过去太喜欢『找差异』，但其实并不好；很多时候赢是因为在同一件事上做得比别人好，不是因为不同。」*

通读 `docs/DESIGN.md`，以下段落和设计明显带有典型的「为了与众不同而强设差异」的痕迹，值得在后续迭代中高度警惕和重新校准：

### 1. DESIGN §0 第 5 条 & §4.4：「把香港边缘拔高为核心战略，并试图在文案上二选一（§9 第 2 条）」
* **原文表现**：*「大陆可达是楔子，全球可用是底线……对外文案先说全球还是先说大陆（产品两边都能用，文案只能先说一边）。」*
* **诊断**：这是典型的「地理差异化执念」。用户不会因为你的服务器在香港而买单，用户只在乎「我的朋友在微信里点开卡不卡、海外的评委点开快不快」。把「香港」作为一个物理卖点向用户宣讲是错位的。
* **纠偏建议**：边缘节点放在香港是优秀的**工程实现手段**，不应包装为产品核心卖点。文案根本不需要纠结「先说大陆还是先说全球」，文案永远只说：**「一条命令，把游戏发到任何人面前，几秒就能玩」**。

### 2. DESIGN §2.3 第 1 条：「上传路径不是差异化，是入场券；差异化在隧道与上传共存」
* **原文表现**：*「每一个零件都有人做得不差，我们的机会在组合（上传与隧道同一条命令）和地理……上传路径不是差异化，是入场券。」*
* **诊断**：低估了「把上传路径本身做到极致」的威力。DESIGN 将上传视为人人都有的平庸入场券，而寄希望于「隧道与上传共存」这一复合特性来制造差异。然而，从 The Gaming Nest、itch.io 和 Unity Play 的现状来看，**现有的上传路径漏洞百出**（Unity Play 频繁 500、The Gaming Nest 不支持多线程、itch.io 必须打包且大陆极慢）。
* **纠偏建议**：把「上传构建拿链接」做到全网最快、预压缩最好、错误提示最准，它本身就能成为压倒性的杀手级能力，而不需要仅仅依赖「同时支持隧道」来撑场面。

### 3. DESIGN §4.5 & §7：「为自托管设计过度的架构包袱（SQLite 降级兼容、AGPL）」
* **原文表现**：*「自托管的人一台机器跑通是 §7 的承诺……SQL 只用两边都有的子集，迁移时改的是连接层不是查询……边缘与控制面 AGPL 且可自托管。」*
* **诊断**：典型的「开源极客自嗨式差异化」。为了照顾假想中的「自托管用户」，让控制面 SQL 拘泥于最低公共子集，牺牲后续数据分析与统计排队的开发效率。真正使用 playtest 的游戏开发者，99% 希望官方托管好一切。
* **纠偏建议**：CLI 开源足够建立信任。服务端开源作为副产物即可，切忌让「为了让别人自托管单机跑通」成为架构演进和功能迭代的掣肘。

### 4. DESIGN §8.3「留门但不推进」：对「画面录像」的过度防备
* **原文表现**：*「画面录像（Playset 的核心卖点）……只有 T6 显示文字反馈被大量使用而开发者反复要『看他当时的画面』时再评估。」*
* **诊断**：为了与 Playset 划清界限（找差异），断然将录像完全打入冷宫，甚至将「反馈附带截图」也推迟到 v0.2。事实上，游戏测试中「一图胜千言」，纯文字经常无法描述跳跃穿模或渲染穿帮。
* **纠偏建议**：不做沉重的全程视频录制是正确的，但不能因此放弃视觉凭证。在 v0.1 的反馈组件中，应当保留基于 Canvas 的轻量一键单帧截图（尽力而为），让文字反馈真正可用。

## 六、对 playtest.run 的含义：支持、冲突与改进建议

### 1. 支持 DESIGN.md 现有的结论
1. **支持坚决不做录像平台**：Playset 证明了按分钟收费录屏不仅极度昂贵，而且把产品做成了一个小众且沉重的用研外包工具，偏离了独立开发者快速迭代的飞轮。
2. **支持开发者端免登录 24 小时匿名链接**：M1（手机上自己试一下）是极高频动作，消除一切注册门槛是体验打磨的第一法则。
3. **支持双域名彻底隔离**：`*.playtest.run` 承载用户动态内容，`playtest.sh` 承载核心控制台与身份，从根本上隔绝了 Cookie 投毒风险，并为可能的微信单域拦截准备了防火墙。
4. **支持对 wasm、预压缩、Range 和 COOP/COEP 的深度支持**：这是游戏有感的核心体现，也是通用工具无法逾越的护城河。

### 2. 与 DESIGN.md 冲突的发现
1. **低估了上传模式的独立价值**：DESIGN 认为上传是红海入场券，但在实际测试与竞品调研中，现有上传工具（TGN、itch butler、Unity Play）由于缺少大陆 CDN、缺乏 SharedArrayBuffer 适配、流程繁杂，依然存在巨大的体验洼地。把上传做好本身就是巨大突破。
2. **门禁页的玩家认知摩擦被轻视**：DESIGN 将门禁页视为理所当然的妙招，但在玩家视角下，任何多余的阻拦都是潜在流失点。若门禁页出现加载迟滞，极易被误解为恶意跳转或 ngrok 式安全警告。
3. **自托管承诺过度束缚了控制面演进**：将 SQLite 与 Postgres 兼容、单机一键 compose 部署作为关键约束，增加了控制面抽象成本，而目标用户几乎无人有自建意愿。

### 3. 具体修改建议（供后续修订 DESIGN.md 参考）
1. **重构宣传聚焦点**：不要在对外定位中过分渲染「香港/隧道与上传组合」等机制性词汇，直接聚焦于最终价值：**「专为 Web 游戏打造的一键极速分发与测试平台：0 配置支持 WebAssembly，微信点开即玩，秒级知道测试结果」**。
2. **门禁页极简化与透明化**：
   * 门禁页务必保持极致秒开（代码量控制在 3KB 内），视觉风格与游戏标题保持高度亲和，消除「中转阻断」感；
   * 提供「开发者可关闭门禁页」的配置项（对于纯开发阶段或无需声音手势的作品，允许直接直通游戏）。
3. **加速轻量反馈（带单帧截图）的优先级**：
   * 将单帧 Canvas 截图功能从 v0.2 提前到 v0.1。文字反馈如果缺少画面支撑，对游戏 bug 定位的帮助将大打折扣。
4. **放宽对自托管的架构约束**：
   * 控制面以服务好托管版的高并发统计与分析为第一优先级，避免因照顾自托管单机环境而对数据库设计做过度妥协。
